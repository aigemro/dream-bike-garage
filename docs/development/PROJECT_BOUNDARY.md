# 메인 프로젝트와 Lab 운영 경계

## 목적

Dream Bike Garage는 완성 게임을 관리하는 **메인 프로젝트**와 기술 대안을 실험하는 **Lab**을 분리하여 운영합니다.

- 메인 프로젝트: 무엇을 만들고 어떤 경험을 제공할지 결정하며, 검증된 기술안을 선택해 최종 게임에 적용합니다.
- Lab: 결정이 필요한 기술 문제에 대해 여러 대안을 구현하고 같은 기준으로 비교·검증합니다.

## 저장소별 책임

| 구분 | 메인 프로젝트 | Lab |
|---|---|---|
| 중심 질문 | 무엇을 만들 것인가? 어떤 안을 채택할 것인가? | 어떻게 구현할 수 있는가? 어떤 기술안이 더 적합한가? |
| 주요 작업 | 기획, 게임 규칙, 화면·데이터 설계, 채택 결정, 최종 적용 | 기술 설계, 프로토타입 구현, 비교 실험, 성능·호환성 검증 |
| 산출물 | 기획·설계 문서, 선택 근거, 최종 코드와 에셋 | 실행 가능한 대안, 평가 결과, 한계와 기술 권고 |
| 이슈 제목 | `[기획]`, `[설계]`, `[적용]` | `[실험]`, `[기술]`, `[검증]` |
| 완료 기준 | 최종 게임에 반영되고 기획 의도를 충족함 | 재현 가능한 결과와 비교 근거를 메인에 전달함 |

## 표준 진행 흐름

1. 메인 프로젝트에서 기획 의도, 플레이 규칙, 제약과 평가 기준을 확정합니다.
2. 기술 대안 비교가 필요하면 연결된 Lab 이슈를 만듭니다.
3. Lab에서 대안을 구현하고 동일한 기준으로 비교합니다.
4. 메인 프로젝트에서 결과를 검토해 채택, 조건부 채택, 보류 또는 폐기를 결정합니다.
5. 채택된 안을 메인 구조와 품질 기준에 맞게 최종 구현합니다.
6. 두 이슈에 서로의 링크와 결정 결과를 남깁니다.

## 이슈 판단 기준

다음 질문에 **예**라면 메인 프로젝트 이슈입니다.

- 게임 콘셉트, 규칙, 사용자 경험 또는 콘텐츠를 정하는가?
- 화면에 무엇을 보여주고 어떤 행동을 허용할지 정하는가?
- 게임 데이터의 의미, 보상, 성장 또는 밸런스 정책을 정하는가?
- Lab 결과 중 최종 채택안을 선택하는가?
- 선택된 기능을 출시 가능한 게임에 적용하는가?

구현 방법이 하나로 정해지지 않았거나 조작감·성능·플랫폼 호환성을 실제 코드로 비교해야 한다면 Lab 이슈를 연결합니다.

## 대표 예시

### 머지 코어

- 메인: 머지 규칙, 주문과의 연결, 실패 조건, 평가 기준 정의
- Lab: 자유 보드형·주문 중심형·체인형 등 기술 대안 구현 및 비교
- 메인: 결과 검토, 방식 선택, 최종 게임 적용

### 저장

- 메인: 어떤 진행 정보가 보존되어야 하는지와 초기화·복구 정책 정의
- Lab: localStorage·IndexedDB·서버 저장의 성능과 제약 비교
- 메인: 채택된 방식으로 실제 게임 데이터 저장 구현

### 앱인토스

- 메인: 출시 범위와 로그인·결제·광고 적용 정책 결정
- Lab: WebView, SDK, 입력, Safe Area, 라이프사이클 호환성 검증
- 메인: 검증된 기술을 출시 빌드에 적용

## 이슈 작성 규칙

메인 이슈에는 다음 내용을 포함합니다.

- 해결하려는 사용자·게임 경험 문제
- 기획 의도와 범위
- 확정된 규칙과 아직 결정되지 않은 항목
- Lab에 검증을 요청할 질문과 공통 평가 기준
- 연결된 Lab 이슈
- 선택 결과와 선택 이유
- 최종 적용 완료 조건

Lab에서 기술적 결정이 필요해진 경우 메인 이슈의 범위를 임의로 바꾸지 않고, 질문과 제약을 메인 이슈에 먼저 기록합니다.

## 코드와 문서 반영 원칙

- Lab 코드는 검증용이므로 메인에 그대로 복사하는 것을 기본으로 하지 않습니다.
- 선택된 개념과 결과를 메인 아키텍처, 테스트, 데이터 정책에 맞게 재구현합니다.
- 실패하거나 보류한 결과도 선택하지 않은 이유를 남겨 재검토 비용을 줄입니다.
- 최종 기획·설계와 출시 상태의 단일 기준은 메인 저장소입니다.
