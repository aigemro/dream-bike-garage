# AI 도구 병행 운영 규칙 (Claude / Codex)

이 프로젝트는 요일에 따라 서로 다른 AI 코딩 도구를 사용합니다.

- **주말**: Claude (Claude Code)
- **평일**: Codex

목표는 하나입니다. **어느 도구로 작업하든 진행 방식과 결과물이 동일해야 하며, 도구를 바꿔도 이어서 작업하는 데 아무 문제가 없어야 합니다.**

## 1. 단일 기준 원칙 — 규칙은 AGENTS.md 한 곳에만

- 에이전트 공통 규칙의 단일 기준(source of truth)은 [AGENTS.md](../../AGENTS.md)입니다.
  - Codex는 `AGENTS.md`를 직접 읽습니다.
  - Claude는 `CLAUDE.md`를 읽고, `CLAUDE.md`는 `AGENTS.md`를 기준으로 따르도록 선언되어 있습니다.
- **작업 규칙을 새로 정하거나 바꿀 때는 반드시 `AGENTS.md`에 적습니다.**
  - `CLAUDE.md`에는 규칙을 새로 쓰지 않습니다. Claude에게만 필요한 맥락 보강(문서 지도 등)만 둡니다.
  - 특정 도구 설정 파일에만 규칙을 적으면 다른 도구가 그 규칙을 모른 채 작업하게 되어, 도구에 따라 결과가 달라지는 원인이 됩니다.
- 도구별 파일의 역할 경계:

| 파일/디렉터리 | 역할 | 수정 주체 |
|---|---|---|
| `AGENTS.md` | 공통 작업 규칙 (단일 기준) | 두 도구 모두. 규칙 변경은 여기서만 |
| `CLAUDE.md` | Claude용 맥락 보강 (규칙 아님) | Claude 세션에서만 관리 |
| `.claude/` | Claude 전용 설정·스킬·워크트리 | Claude 전용. Codex 세션에서 수정 금지 |
| Codex 전용 설정 파일 (생기는 경우) | Codex 전용 설정 | Codex 전용. Claude 세션에서 수정 금지 |

## 2. 작업 상태는 Git과 GitHub에만 남긴다

AI 세션의 대화 내용, 세션 메모리, 로컬에만 있는 미커밋 변경은 **도구를 바꾸는 순간 사라지는 정보**입니다. 인수인계 매체는 오직 다음 세 가지입니다.

1. **GitHub Issue** — 무엇을, 왜 하는지. 진행 상황과 남은 일
2. **브랜치와 커밋** — 실제 작업 내용 (반드시 push까지)
3. **Pull Request** — 리뷰 대상과 완료 조건 (`Closes #번호`)

따라서:

- AI에게 "지난번에 하던 거 이어서 해줘"라고 하지 않습니다. 대신 Issue 번호나 브랜치 이름으로 지시합니다.
  - 예: "#42 이슈의 `feat/merge-board` 브랜치 이어서 작업해줘"
- AI가 세션 중 발견한 제약, 결정 필요 사항, 남은 TODO는 **Issue 코멘트로 남기게** 합니다. 대화에만 남은 내용은 없는 것으로 간주합니다.

## 3. 세션 시작 체크리스트 (두 도구 공통)

어느 도구든 작업을 시작할 때 아래 순서를 따릅니다.

1. `git fetch` 후 `main` 최신 상태 확인 — 다른 도구가 병합한 작업을 먼저 반영
2. 작업할 Issue 확인 (없으면 Issue부터 생성)
3. 해당 Issue에 이미 연결된 브랜치·PR이 있는지 확인 — 있으면 그 브랜치에서 이어서 작업
4. 새 작업이면 `main`에서 `feat/*`, `design/*`, `fix/*`, `chore/*` 브랜치 생성

## 4. 세션 종료(인수인계) 체크리스트 (두 도구 공통)

세션을 끝낼 때, 특히 **주말↔평일 도구 전환 직전**에는 반드시:

1. 작업 중인 변경을 전부 커밋 — 미완성이어도 WIP 커밋으로 남깁니다 (커밋 메시지는 한국어)
2. 브랜치를 원격에 push — 로컬에만 있는 커밋은 인수인계되지 않은 것입니다
3. Issue(또는 PR)에 진행 코멘트 작성:
   - 완료한 것 / 진행 중인 것 / 다음에 할 것
   - 세션 중 내린 판단과 그 이유 (특히 기획 판단이 아닌 구현 판단)
   - 막힌 부분, 결정이 필요한 부분
4. 테스트·빌드 상태 명시 — `npm test`, `npm run build` 통과 여부. 실패 상태로 넘기는 경우 실패 내용을 코멘트에 기록

## 5. 동시 작업 충돌 방지

- **하나의 Issue·브랜치는 한 시점에 하나의 도구만 작업합니다.** 같은 브랜치를 Claude와 Codex가 번갈아 쓰는 것은 괜찮지만, 동시에 두 세션을 열지 않습니다.
- 도구 전환 시점(금요일 밤 / 일요일 밤)에 위 인수인계 체크리스트를 완료한 뒤에만 다음 도구로 넘어갑니다.
- 서로 다른 Issue를 다른 도구로 병행하는 것은 가능하지만, 같은 파일을 크게 건드리는 작업은 겹치지 않게 Issue 단계에서 분리합니다.

## 6. 결과물이 도구와 무관하게 동일해야 하는 항목

아래는 도구가 무엇이든 똑같이 지켜야 하는 기준이며, 전부 `AGENTS.md`와 기준 문서에 정의되어 있습니다.

| 항목 | 기준 |
|---|---|
| 코드 구조 | `src/domain`(Phaser 비의존 순수 규칙) / `src/game`(Phaser 표현) / `src/ui` — [ARCHITECTURE.md](ARCHITECTURE.md) |
| 밸런스 데이터 | `src/data`의 명시적 타입으로 관리 |
| 테스트 | 규칙 변경 시 `tests/` Vitest 테스트 동반 갱신 |
| 검증 순서 | `npm test` → `npm run build` (커밋 전 로컬에서, CI에서 동일 실행) |
| 브랜치·PR | Issue → `feat/*` 등 브랜치 → PR(`Closes #번호`) → 리뷰 → 병합 — [WORKFLOW.md](WORKFLOW.md) |
| 언어 | 커밋 메시지·주석·문서는 한국어, 변수·함수명은 영어 |
| MVP 범위 | [MVP.md](../game-design/MVP.md) 밖 기능은 구현하지 않음 |
| 기획 판단 | AI나 개발자가 임의 확정하지 않고 Issue로 공유 |
| 실험·검증 | 메인 저장소가 아닌 [Lab 저장소](https://github.com/aigemro/dream-bike-garage-lab)에서 — [PROJECT_BOUNDARY.md](PROJECT_BOUNDARY.md) |

AI가 위 기준과 다른 방식을 제안하면 채택하지 않고, 기준을 바꿔야 한다고 판단되면 먼저 `AGENTS.md`(또는 해당 기준 문서)를 고치는 PR을 별도로 만듭니다.

## 7. 도구별 특이사항

### Claude (주말)

- `CLAUDE.md`와 `.claude/` 설정을 사용합니다. 이 안의 내용이 `AGENTS.md`와 어긋나면 `AGENTS.md`가 우선입니다.
- Claude가 워크트리(`.claude/worktrees/*`)에서 작업한 경우에도 결과는 일반 브랜치 push + PR로 남기므로 인수인계 방식은 동일합니다.

### Codex (평일)

- `AGENTS.md`를 직접 읽습니다. 별도 설정 파일을 도입하게 되면 위 역할 경계 표에 추가합니다.
- Codex 세션에서 `CLAUDE.md`, `.claude/`를 수정하지 않습니다.

## 8. 규칙 변경 절차

이 문서나 `AGENTS.md`의 규칙을 바꿀 때:

1. `chore/*` 브랜치에서 문서 수정 PR 생성
2. 두 문서가 어긋나지 않는지 확인 (`AGENTS.md`가 항상 상위 기준)
3. 병합 후 다음 세션부터 두 도구 모두 새 규칙 적용
